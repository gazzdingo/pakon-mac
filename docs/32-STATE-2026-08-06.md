## THE DIAGNOSIS, SETTLED

**U34 (PICM, motor control) is dead. It needs replacing.**

This is established by control, not inference:

| | |
|---|---|
| U11 (PICL) over ICSP | **Reads perfectly.** `PIC18F452 found, Revision ID 7`, full flash three times byte-identical |
| U34 (PICM) over ICSP | **Device ID `0x0`**, or no response at all |
| Same programmer, same cables, minutes apart | The variable is the chip |

U34 is also silent on I2C at all 128 addresses, while its pins are **proven
electrically connected to the bus** (pin 37 → VDD 5.42 kΩ, pin 42 → 1.05 kΩ,
both reading the bus pull-ups). So it is not a broken trace. The chip is dead.

Everything else on the machine works: light board, lamp, CCD, FPGA, USB.

### ICSP headers — MEASURED, not assumed

Two 5-pin headers. **`JM11` serves U34**; the other serves U11.

| Header pin | → chip pin | Measured | Signal |
|---|---|---|---|
| 1 | 18 | **470 Ω** | MCLR/VPP |
| 2 | 28 | connected | VDD |
| 3 | chassis | connected | VSS |
| 4 | 17 | **100 Ω** | PGD |
| 5 | 16 | **100 Ω** | PGC |

**GOTCHA:** pins 1, 4, 5 have series resistors, so a **continuity/beep test
reads them as OPEN**. Use resistance mode. This misled us for hours.

### The two irreplaceable things, and their status

1. **Per-unit calibration** (`0x52`) — magnification, optical alignment, motor
   speeds, unique to this scanner. **SAFE.**
2. **A Kodak PIC18 bootloader** — recovered from U11. **SAFE.**
   As far as we have looked, `u11-full-A.hex` is the **only copy of a Kodak
   bootloader, of any core, in existence.** No vendor file contains one: 348
   HEX images all start at `0x400` (PICM) or `0x340` (PICL), and the PIC16
   images that do include `0x0000` are older *pre-bootloader standalone builds*.

### THE READ TRAP — external EEPROMs only

`0x51`/`0x52` return good data on the **FIRST** transaction after a power cycle
and **degrade on every read after it**. Second read differed in 180/256 bytes;
by the third both read all `0xFF` — while still returning status `ok`.

A repeated-read hash comparison therefore converges on **stable garbage**. A
7-pass run reported "STABLE, trustworthy" for 256 bytes of `0xFF`.

**Correct protocol: power cycle, ONE read, compare against first-reads from
OTHER power cycles.** Use `tools/eeprom_oneshot.py`.

ICSP does **not** behave this way — three back-to-back U11 reads were identical.

## WHAT IS BUILT AND READY

`build/build_picm_image.py` produces two images for the replacement chip:

* **`build/picm-staged.hex`** — bootloader + `nm0506` + config, **no EEPROM**.
  A fresh chip reads `0xFF` at EEPROM index 0, which is not `0xAA`, so it
  should stay in the bootloader and answer I2C `0x46`. **Nothing moves.**
  Program this first.
* **`build/picm-run.hex`** — same + `EEPROM[0]=0xAA`, application runs, `0x44`.

Bootloader patches (from `docs/31`, each 'from' byte verified before writing):

| Addr | From | To | Why |
|---|---|---|---|
| `0x0008` | `A4 EF 01 F0` | `04 EF 02 F0` | ISR forward → `0x408` |
| `0x0018` | `80 EF 1E F0` | `04 EF 02 F0` | dead vector made inert |
| `0x0044` | `A0 EF 01 F0` | `00 EF 02 F0` | app-valid hand-off → `0x400` |
| **`0x005C`** | **`42`** | **`46`** | **the I2C slave address** |
| `0x01D8` | `3E` | `FE` | write-guard floor `0x33E` → `0x3FE` |
| `0x0266` | `A0 EF 01 F0` | `00 EF 02 F0` | command-8 hand-off → `0x400` |

Config comes from **`nm0506.HEX`** (`00 26 06 0d 00 01 81 00 0f c0 0f e0 0f 40`),
NOT U11's — they differ and the bootloader never sets `CFGS`.

**STATUS: under adversarial review by a subagent. Do not program until that
review is read.** Key open question: does a blank EEPROM genuinely hold the
chip in the bootloader, or could a fresh chip run the application immediately?

## THE TOOLCHAIN (works natively on this Apple Silicon Mac)

MPLAB X v5.50 + PICkit 3. `ipecmd` needs **two** things or it fails:

```
<mplabx>/sys/java/zulu8*x64*/zulu-8.jre/Contents/Home/bin/java \
  -Djava.library.path=<mplabx>/mplab_platform/bin \
  -jar <mplabx>/mplab_platform/mplab_ipe/ipecmd.jar \
  -P18F452 -TPPK3 -OD -GF<outfile>
```

* **bundled x64 JRE** — system `java` is arm64 and cannot load
  `libUSBAccessLink_3_36.dylib`, which is x86-only
* **`-Djava.library.path`** — without it: "Programmer not found"
* **`-OD`** = VDD before VPP. Safer ordering
* **Do NOT pass `-W`** — verified against the installed help, `-W` means
  "power target FROM TOOL". Omitting it means externally powered, which is what
  we want. A review once claimed the opposite; the binary settles it.

`tools/icsp_read_all.py` wraps this with 5 reads, per-region SHA-256 and trust
gates. `tools/flash_diff.py` diffs against `nm0506`. Both self-test 7/7.

**Write interlock**: `tools/WRITES_LOCKED` blocks 11 tools that can write.
Leave it in place.

## SAFETY FINDS WORTH REMEMBERING

* `tools/picm_read_flash.py`'s fetch packet uses `07`. **One bit away**:
  `0x0B` writes 16 bytes, `0x0F` erases a row at the latched address.
* MPLAB programming **BULK-ERASES the whole chip** — program memory, EEPROM
  and config — before writing. Any image programmed must therefore be a single
  merged file containing everything. `nm0506.HEX` alone would erase the
  bootloader and not write it back.
