**Method note:** I extracted `PakonIMAu.dll` from `research/sdk/PAKONF135.iso` (`fx35install/program files/Pakon/F-X35 COM SERVER/PakonIMAu.dll`, sha256 `0ede8d98…`) into a scratch dir and analyzed it fresh with radare2 6.1.8 (no repo files touched, no r2ghidra decompilation needed — plain disassembly + raw byte scans sufficed). I independently re-derived the "walk direct calls" method this project already uses, and **calibrated it against both reference numbers in the prompt before trusting it on fos**: it reproduced Shasta's 189 functions exactly, 44,378–44,432 bytes (vs. quoted 44,427 — the "size" field r2 reports as `max−min` address span is unreliable when a stray far edge inflates it; summing `realsz` per function fixes this), and 386 indirect call sites exactly (definition that matched: any `call` whose operand is a register or memory dereference, not sym.imp inclusive/exclusive both tried — text-form classification, not r2's `type` field, was what matched). It also reproduced analyzeAutoTone's 166-function whole-chain count exactly. This is real measurement, not an assumed match.

- The "fos" capability-name string (`0x105740e4`) is pushed at `0x1006abc4`, inside a block whose companion error strings cite `\Atc\ansel\src\libPaths.ansel\CN-Enhanced.cpp` — i.e. this is inside **AnsCnEnhancedPath's own declare code**, in straight-line, unconditional sequence (`fos` → `scpLut` → `afterSCPLutFos`/`afterSCPLutSba`, matching the previously-recorded producer order). No jump table, no filmClass branch skips it — unlike Shasta, which is provably dead (no CN-Premium case reaches it).
- `AnsFosCapability::analyze` (Cap-level) is called at `0x1010194d`, inside a function that self-identifies via the embedded string "ColorNegativePath::analyzeBalanceOrder" (same `cnMethods.cpp` file that hosts `analyzeAutoTone`). The only guard around the call is a null-pointer check, not a path/filmClass test.
- **Verdict: fos is genuinely declared *and* genuinely executed** (acquire → Cap::analyze → Impl::analyze all run) for AnsCnEnhancedPath / a colour negative. This is a live call, not the Shasta situation.

### 4. What it writes, and its plausible tone relevance
- FOS's write target is its own `Impl+0x18` **OUT block** (`SbaFOSResults`, 36 bytes) — not a field directly inside `AnsSceneContext`'s own struct. The FOS Capability *object* (holding this block) is what's registered under the name `"fos"` in the scene, so any later `find("fos")` gets access to it. Fields (per `pakon_fos.py`, itself Unicorn-verified): `orderFpo[3]`, `fosOrderAvg[3]`, `fosDmin[3]`, `gmSlope`, `gmOffset`, `illSlope`, `illOffset`, `theta`, `ofpoMethod`, `numPixels`, `gmRSquare`, `illRSquare` — all density-regression statistics (paxel-based density-vs-order-number regression, gray/illuminant slope+offset+R²). This content is unambiguously density/exposure-shaped, not geometric/cosmetic.
- **New finding from this session:** direct-call reachability from `analyzeAutoTone` (166 functions) contains **zero** references to the literal `"fos"` string. The only literal-named `AnsSceneContext::find()` calls inside that chain are two lookups of `"lighting"` inside `AnsDraCapabilityImpl::analyze` (already documented elsewhere as unreachable for CN-Enhanced). There is one generic, dynamically-named per-capability iteration loop reached several calls deep in the "contrast" branch (`0x10297d90`, via `0x101d5270→0x101d3fa0→0x10257b90`) that calls `find()` using each already-declared capability's own vtable-provided name — it plausibly touches fos generically (verify/AddRef-style vtable calls) but does **not** read any of FOS's specific OUT fields.
- FOS's real, already-verified consumption path (per `pakon_fos.py`, citing `docs/47`/`docs/48` which aren't present in this checkout) is: it runs *between* SBA's `analyzePass1` and `analyzePass2` inside `analyzeBalanceOrder`, feeding the roll/scene-balance mechanism that drives `ColorNegativePath::setShifts` → the three per-channel integer shifts `analyzePostBalance` applies (`lut_c[i] = master[i+shift_c]`) — a real but *separate* exposure/density mechanism from the `analyzeAutoTone` 6-subsystem tone-curve chain this task centers on. It's also already-VERIFIED (`FOS_TO_PREFERENCE_FPO_EDGE = False`) that FOS does not statically write into the nested Preference `fpo` opening-RGB field.
- **Net:** fos's output is tone/density-shaped and plausibly reaches the negative's exposure balance via SBA/setShifts, but I found no evidence (static, direct-call) that `analyzeAutoTone` itself consumes it.
