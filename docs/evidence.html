Kodak Pakon F-135 Plus · macOS port · evidence log

Every claim, how we know it, and where to check

Each entry states a claim, the method that established it, and the exact file, address or measurement it rests on. Nothing here asks to be taken on trust — the point is that you can go and verify it.

Verified Refuted Inferred

01What broke it

A single packet, sent blind during a sweep of an unidentified command space. What follows is the attempt that sent it, why it looked safe at the time, and why that reasoning was wrong.

The attempt: hunting for a command that would open the optical path
The goal
Situation
The lamp was lit — bright blue, operator-confirmed — but the sensor endpoint EP 0x86 sat at a constant mean of ~1240 and would not move. Light was being produced but was not reaching the sensor.
Hypothesis
The F-135 has a filter wheel, and a wheel parked in the blocked position produces exactly that. Three separate symbols in TLB.dll supported it: FN_bDrvMoveFilterWheel, EC_MotorFault_FilterWheel, and the enum value FILM_COLOR_FILTER_WHEEL_BLOCKED.
Plan
Light the lamp, then walk the motor board's entire Type 4 command space watching the sensor level. If a command opened the path, the level would jump immediately and unambiguously. Quoting the tool's own header: "walk the motor board's Type 4 command space watching the sensor."
Ran
./find_light_path.py — default board 0x44, the motor board. All 256 commands, skipping only {0x00, 0xA0, 0xA1, 0xA2} as already-known transport commands. 0x0D was not on that skip list.
Source
tools/find_light_path.py:2-25 (intent) · :40 (skip list) · :130-133 (the sweep)
Why it looked safe — and why that reasoning was wrong
Bad assumption
The claim
Written into the tool's header as its safety argument, verbatim: 
Only Type 4 commands are used. They are the vendor's own
command form, and the board rejects unknown ones with
status 2 rather than acting on them.
The flaw
That is true of unknown commands — and 0x01 through 0x0D were not unknown. They were real, implemented vendor commands whose effects had simply never been established. The tool logged them as "accepted" and moved on, which is precisely what a command doing something drastic looks like.
The gap
The sweep's only success test was does the sensor level jump (mn > base * threshold). It had no test for did that command do something irreversible. A board reset and a bootloader jump both register as "accepted, no light."
The lesson
"The board rejects what it doesn't recognise" protects against invalid input. It offers no protection whatsoever against valid input whose meaning you haven't looked up. Sweeping a command space is only safe once you know what the commands in it do — which is the thing a sweep is being used to avoid finding out.
Source
tools/find_light_path.py:18-20 (the assumption) · :140-150 (the success test)
The breaking packet was 04 03 44 00 0d — Type 4 command 0x0D to the main board
Verified
How
The sweep's own log recorded "commands 0x01–0x0d accepted" and nothing after. That does not mean only low commands are valid — it means the board answered up to 0x0d and then stopped. Everything from 0x0e to 0xff was NAKed because nothing was left to answer.
Firmware
In nm0506.HEX, command 0x0D dispatches 0x001DAC → 0x001ABE → GOTO 0x000000 — a jump into the bootloader. Command 0x01 is 0x001DA8 → 0x001AAE → RESET.
Damage
Bootloader entry erases the application's vector rows. Exactly 0x000400–0x00047F was later found blank — 128 bytes, two 64-byte rows, which is the only shape a PIC18 row erase produces.
Source
tools/find_light_path.py:130-133 · Config/Firmware/nm0506.HEX · docs/25
Two bugs in my own tooling hid the damage for hours
Verified
Bug 1
Writes were reported ok on any response, without checking the status byte. After the board went silent, every CCD register write was being NAKed while the tools printed success. A write is accepted only when resp[0] == 0x07 and resp[3] == 0x00.
Bug 2
Register reads are two packets, not one. Every dump taken before the fix recorded the request echoing back rather than data. 
01 03 <board> <n> <reg>   request
01 03 <board> <n> 07      fetch → 01 <n+3> <board> <status> <data...>
Proof
With the correct form, host 0x10 register 3 returns 01 04 10 88 0f 03 = FX2 firmware v3.15. The single-packet form returned the request echo. Visible in the old dump: board 0x40 reg 0x94 read 82 94, reg 0x95 read 82 95.
Source
TLB.dll fcn.10009410 (FN_bDrvGetByteArrayNL) · ~/pakon-full-dump-*/scanner/boards_registers.json

02What the hardware is doing now

All measured on the device, repeatedly.

The PIC is executing code — its processor, crystal, PLL and timers all work
Verified
How
A diagnostic LED on the main board blinks a stable repeating pattern indefinitely. Frame-by-frame video analysis measured the pulse widths, and they match the firmware's internally-computed constants four times over:

The I²C slave was armed at address 0x44 — and still doesn't acknowledge
Verified
Boot order
Hand-decoded from raw instruction words: 
0x2C6A  GOTO 0x1A8C
0x1A8C  MOVLW 0x36 ; MOVWF SSPCON1    SSPEN=1, I²C 7-bit slave
0x1A90  MOVFF 0x134, SSPADD           = 0x44
0x2C6E  BSF PIE1,3                    SSPIE
0x2C76  IORWF INTCON,F                GIE + PEIE
0x2C8C  BCF PORTA,4                   ← first modulated LED activity
0x2C8E  main loop head
0x2D78  BRA 0x2C8E                    loop closes
Uniqueness
RETRACTED 2026-08-04. This claim previously read: "0x1A8C is reachable only from 0x2C6A … there is no bypass path, so a stable repeating blink proves the I²C peripheral was armed." It does not hold. See below.
Why it fails
A full control-flow analysis (analysis/cfg_v3.py) found:
  • 0x1A8C has two incoming edges, not one — the GOTO from 0x2C6A and a fall-through from 0x1A8A.
  • The blink routine at 0x1682 has no incoming edge at all in the static graph, so "the blink engine is called only from the main loop" is unverified.
  • Backward tracing from 0x1A8C reaches 44 nodes and never connects to the reset vector. Forward reachability from every vector covers only ~6% of the image (321 of ~5,300 words).
  • 0x408 holds MOVWF 0x05 — plain code, not a vector jump. The real ISR entries are at 0x0008/0x0018, inside the bootloader we cannot read, and are forwarded from there. So "no interrupt handler touches RA4" is not establishable by static analysis at all.
Consequence
The inference "it blinks, therefore MSSP was armed, therefore the fault is electrical" is not supported. That inference was part of why the hardware hypothesis was leading. Removing it moves weight back toward firmware or persistent state — the direction the owner argued for repeatedly. Only the flash read settles it.
Yet
Every probe returns 07 02 44 01. Status 1 is EC_DRV_PacketHostErrorNoAck — no I²C acknowledgement at all. That is a hardware-level fact, not an application decision.
Source
nm0506.HEX · TLB.dll fcn.100087a0 (status decode)
The I²C bus itself is good
Verified
How
The light board sits on the same two wires, reached across a cable connector, and answers everything — commands, register reads, lamp control. The PIC is on the same board as the FX2, inches away, and doesn't.
Readings
Light board 0x40: reg 0x02 → 0x02; reg 0x83 → 0x12; reg 0x84 → 0x0280; reg 0x88 → 0x0282, 0x01F2. Plausible, distinct, repeatable values.
Also
Because the light board ACKs, neither SCL nor SDA is being held low by anything — including the PIC.

03Eliminated by evidence

Each of these was a working hypothesis at some point. Each was killed by a measurement or a fact in the binary, not by argument.

Flash corruption
Refuted
Why
The application physically cannot write flash: nm0506 contains no TBLWT instruction and never sets EEPGD. The flasher cannot emit an address below 0x400. Pre-repair reads matched factory-programmed content at 0x800, 0x1000 and 0x2000.
Source
nm0506.HEX (instruction scan) · tools/flash_picm.py:209-236
Wrong firmware revision — the reset vector jumping to the wrong entry point
Refuted
Why
Diffing all five nm* images shows 0x480 is identical in every one, and 0x800 only separates the oldest two. 0x1000 and 0x2000 are the addresses that discriminate nm0406 from nm0506 — and both were read and both matched nm0506.
Corroboration
The PCB is silkscreened #125430 REV C. Per ReadmeF135.txt, NM05yy is the image for PCB #125430C.
The deliberate EEPROM write 02 05 44 02 0a 00 aa broke it
Refuted
What it actually is
A raw write of 0xAA to PIC internal EEPROM address 0 — the bootloader's "application is valid, run it" flag. It is exactly what Kodak's own updater sends after every firmware update.
Why it can't be the cause
The application never reads EEPROM addresses 0 or 1. Every EEADR load in the image comes from a literal, and the literals are 2, 3, 4, 5, 6. Exhaustive, not sampled.
Source
TLB.dll FN_bUpdate ~0x1001CC56 · nm0506.HEX EEADR literal scan
The stray EEPROM write from the sweep broke the I²C
Refuted as the cause
The write is real
Command 0x0A is an EEPROM write taking address and data from packet bytes a Type 4 command doesn't populate — so the sweep wrote EEPROM[stale] = stale from leftover buffer contents. Best reconstruction: EEPROM[4] = 0x0D, from the gain-restore packet 02 06 44 03 84 04 0d 00 sent just before. Corroborated: probe_sensor_path.py:115 restores "default gain 13" on exit — and 13 is 0x0D. The stray value in the buffer is accounted for exactly, by a different tool, run just beforehand.
But
On a cold boot the application never reads EEPROM before arming the I²C peripheral, and no fault state anywhere touches SSPCON1 or SSPADD. It likely explains the fault code and the orange front-panel LEDs. It cannot explain the missing acknowledgement.
Source
tools/probe_sensor_path.py:115-117 · nm0506.HEX:0x1956 (cold/warm branch)
A corrupted address literal — the chip answering somewhere unexpected
Refuted
Test 1
Type 4 write sweep, all 256 addresses → only 0x10, 0x40, 0x41, 0xa2–0xa5. All accounted for.
Test 2
Type 1 read sweep, all 256 addresses → only 0x10, 0x40, 0x41. Both transaction directions, every address.
Test 3
The board answered correctly at 0x44 immediately after the vector repair and accepted a full CCD bring-up. That can only happen if SSPADD was loaded with 0x44 — so the literal at 0x2C62 was intact, and nothing has written flash since.
Our own probing during boot poisoned the I²C module
Refuted
The mechanism
Genuine and worth testing: on PIC18 a byte left in SSPBUF sets BF, and BF makes the module NAK its own address. The application's I²C init never reads SSPBUF and never toggles SSPEN.
The test
Powered on and sent nothing for 60 seconds, then a single firmware load and one probe. With the FX2 unloaded there is no I²C traffic at all during the PIC's boot, so nothing could poison the buffer.
Result
07 02 44 01 — still NAK. Refuted.

3bRaw I²C scan — 2026-08-04

Custom FX2 firmware, bypassing the vendor protocol entirely. The most sensitive test available without a programmer.

U11 does not acknowledge at any of the 128 I²C addresses
Verified
Why this differs
Every earlier sweep used the vendor packet protocol, whose presence test needs a complete well-formed response (resp[0]==7 && resp[3]==0). A chip that ACKs its address but fails later reads as absent — indistinguishable from silence. A raw scan needs only the address ACK. Far lower bar, far more sensitive. It also covers 7-bit 0x08 (board 0x10), which the FX2 answers itself and had therefore never physically been on the wire.
Method
Purpose-built FX2 firmware (fx2/i2c_scan.c, 375 bytes) driving the FX2's own I²C controller. Each probe: START, device address with R/W set (read direction), STOP. Exactly one write to I2DAT in the whole source, and it is the address — no data byte is ever transmitted. Results read out of RAM over vendor request 0xA0 with the 8051 halted.
Result
Marker c0 de f1 35 — all 128 addresses probed.

Kills
The corrupted address literal hypothesis. If the MOVLW 0x44 at 0x002C62 had been altered, U11 would ACK at whatever address that produced. It ACKs nowhere. Also confirms the earlier refutation of the "PICM at 0x10" idea by direct measurement rather than disassembly.
Does NOT distinguish
"MSSP peripheral dead" from "firmware never reaches the MSSP init at 0x1A8C". Both produce identical silence. Only the flash read separates them.
Caveat
Runs 1–3 were polluted: a read-direction probe leaves an ACKing slave owning SDA, which wedged the bus from 0x52 onward, and an attempted fix that issued STOP before START set BERR on everything. Only the fourth run — after a power cycle, with LASTRD byte-clocking recovery and no pre-STOP — is clean. That is the one tabulated above.
The boot EEPROM is blank — all 0xFF
Verified
Symptom
The scanner enumerates as 04b4:8613, the Cypress hardwired default, not 0f05:f235. It was already in that state before any of today's work.
Read
fx2/eeprom_read.c, read completed cleanly (marker c0 de f1 35, status 0x13 = ACK+DONE on all three phases): 
bytes 0-15:  ff ff ff ff ff ff ff ff ff ff ff ff ff ff ff ff
expected:    c0 05 0f 35 f2 07 aa 04
Meaning
Byte 0 is the format signature; it must be 0xC0 for the FX2 to take VID/PID from the EEPROM. At 0xFF the FX2 ignores it entirely. Fully explains the enumeration. Erased, not corrupted — this is not the same failure as the earlier 0x5C signature damage.
Impact
Cosmetic for diagnosis. The EEPROM supplies only USB identity; it has no bearing on U11 or the I²C fault. pakon_load.py works with an explicit firmware choice.
Note
The repair was previously verified persistent across power cycles. It is now blank, so something erased it since — unexplained, and worth understanding before rewriting it.

04Repaired and verified

Boot EEPROM — restored to Kodak's exact personality
Verified
Damage
An earlier blind sweep across 0xa2–0xa5 — which are I²C EEPROM addresses, not board addresses — corrupted it. Byte 0 is the FX2 format signature; 0xC0 means "take VID/PID from this EEPROM", and it had become 0x5C.
Repair
Written back byte-by-byte to c0 05 0f 35 f2 07 aa 04 02, matching Kodak's shipped USB F135.bin.
Proof
Survives power cycles. The scanner now self-identifies as 0f05:f235 rev aa07 and pakon_load.py selects Pakon7.hex from the device's own personality with no override.
Lesson
A read-back in the same session proves nothing, and neither does a read after a loader reload. Only a power cycle confirms an EEPROM write committed. It took three attempts to learn that.
PICM vectors — 128 bytes restored, verified 8/8
Verified
What
Two 64-byte rows at 0x000400–0x00047F, the reset and interrupt vectors, erased by the bootloader-entry command. Rewritten from nm0506.HEX.
Proof
All 8 blocks read back byte-identical to the vendor image. The board now boots on its own with a green power LED, where previously all three front LEDs were red.

06What remains, honestly

The fault is confined to the PIC's I²C responding — cause not yet determined
Open
Remaining
Either RC3/RC4 are electrically open (a cracked joint or a broken trace), or the MSSP peripheral itself is damaged, or there is flash damage in the ~3 KB above 0x2000 that has never been read back.
Why it's stuck
Reading that flash requires the chip to answer, which is the thing that's broken. Circular — and why a programmer is the way out.
No copy of the PICM bootloader exists anywhere
Verified
How
All 348 HEX files across every install tree were parsed. Every PICM image starts at 0x400, every PICL image at 0x340. No embedded Intel HEX in any DLL or EXE, ASCII or UTF-16. A PIC18 code-density scan across 2,992 files returned zero hits.
Consequence
0x0000–0x03FF was factory-programmed and never shipped. Reading it out is worth doing regardless of how this ends — no copy is known to exist.
On the "90%" figure. That was an estimate, not a measurement. What the evidence actually supports is narrower and firmer: the failure is confined to one chip that is unprotected, still in production, costs about $5, and sits on a board where everything else demonstrably works — with a programming header beside it. No fact in evidence indicates this is unrecoverable. Converting that into a percentage is judgment, and softer than the facts beneath it.
