# scpLut (producer)

## Summary — `scpLut` capability, scoped against `ColorNegativePath::analyzeAutoTone`

All addresses below were verified today against `PakonIMAu.dll` (SHA identical copy at `/tmp/pakon_scratch/PakonIMAu.dll`, `/Users/guy/pakon-windows-repair/COM-SERVER/PakonIMAu.dll`, and inside `research/sdk/PAKONF135.iso`) using radare2 6.1.8, both light `aa` + BFS direct-call walks (the project's established method) and one full `aaa` pass with vtable/RTTI recovery for ground-truth function boundaries and class/method naming. Base `0x10000000`.

**1. Addresses (VERIFIED, all four link up in the debugger, not assumed):**
- `AnsSCPLutCapability::analyze` — `0x101226c0` (943 bytes; xref'd from `ColorNegativePath::analyzeScpLutBalance` at `0x100fd93e`)
- `AnsSCPLutCapabilityImpl::analyze` — `0x102128f0` (301 bytes; xref'd from Cap::analyze at `0x10122777`)
- `AnsSCPLutCapability::acquire` — `0x10122b10` (1201 bytes)
- `AnsSCPLutCapabilityImpl::initialize` — `0x10212130` (1683 bytes)

These match `tools/ansel/python-pipeline/pakon_scp_lut.py`'s already-documented catalog exactly.

**2. Size, direct-call reachability from `AnsSCPLutCapabilityImpl::analyze` (0x102128f0):**
**7 functions / 2,310 bytes / 3 indirect call sites** (BFS walk, same method as the 189/44,427/386 Shasta and 166/67,896/615 autoTone calibration figures — I independently reproduced the autoTone number too: 166 functions and 615 indirect sites matched exactly; total bytes came out 71,760 vs. the documented 67,896, a ~5.6% delta attributable to r2-version function-size accounting, not the walk itself). Callee set: `0x100012e0`, `0x100065e0`, `0x102127d0` (analyze worker), `0x10287eb0` (core: slopes/offsets + LUT fill, 1,097 bytes), `0x1028c4e0` (opponent transform), `0x104ffe44` (ftol2). **scpLut is roughly 25x smaller than the Shasta capability and ~29x smaller than the whole autoTone chain** — a small, self-contained piece, not a soft wall.

**3. Genuinely reachable/executed for AnsCnEnhancedPath — YES, but as a sibling stage, not inside analyzeAutoTone. No filmClass/path gate excludes it (unlike Shasta).**

- **Correction to prior project docs:** `AnsCnEnhancedPath::declare` is **not** at `0x10064d70` (that address is a real function, but it's a 201-byte, single-basic-block, zero-call POD field-initializer with only 6 unrelated callers — nothing to do with capability registration). The real declare is the vtable method r2's RTTI recovery names `method.AnsCnEnhancedPath.virtual_20`, starting at **`0x10068490`** — a single 1,495-byte straight-line basic block that constructs and registers capability name-strings in sequence via a shared helper (`fcn.10025cd0`). Its literal push order is `filmLut, flesh, pan, fos, scpLut, afterSCPLutSba, area, orderOrientation, asea, noiseTable, pnr, nra, dei, dtt, falloff, fugc, cna, dra, toneHelper, contrast, citras, pfd` — an **exact match**, item-for-item, to the order already recorded in `docs/63-port-status.md`/`shasta.go`, just at a different, now-verified address. `scpLut` is the 5th capability declared, immediately after `fos` and before `afterSCPLutSba`. The sibling method for `AnsCnPremiumPath` (`0x10059240`) declares the same name.
- `ColorNegativePath::analyzeScpLutBalance` (`0x100fd190`) has two real callers: `0x100691cd` (inside CN-Enhanced's OrderWide orchestrator, `fcn.100691a0`) and `0x1005a3e0` (CN-Premium's equivalent) — a genuine, path-specific execution edge, not a dead branch.
- `docs/62-colour-engine-consolidation.md` §12.4.1 (this project's own already-established, independently-verified finding) shows `AnsCnEnhancedPath::exportParameterPack` (`0x10065990`) emits a "balance" operand = `BalanceMethods_export` (`0x101142a0`) which composes **`filmLut → scpLut → shift`**, and I independently confirmed today that `0x101142a0` (BalanceMethods_export) and `0x10102b20` (`balanceAreaImage`, which composes `filmLut_c ∘ scpLut_c ∘ shift_c ∘ fugc_c`) both directly reference the string `"scpLut"` — scpLut is definitely on the live CN-Enhanced pipeline, both analysis- and render-side.
- **What I could determine about `analyzeAutoTone` specifically:** none of the 12 sites in the binary that reference the literal string `"scpLut"` fall inside `analyzeAutoTone`'s 166-function direct-call-reachable set (checked against the full-`aaa` verified function boundaries, not the earlier looser probe). Of the 132 `AnsSceneContext::find` call sites in the whole DLL, only 3 are inside that reachable set, and the one identifiable by name is the already-documented `dra` guarded `find("lighting")` at `0x1022b314`. So **`analyzeAutoTone` does not call `AnsSceneContext::find("scpLut")` anywhere in its direct-call reachable set** — scpLut's balance stage (`analyzeScpLutBalance`/`balanceAreaImage`) runs as a sibling stage earlier in CN-Enhanced's scene order (`analyzePostBalance → analyzeFugc → balanceAreaImage → … → analyzeAutoTone`, per `docs/62`), not nested inside it. Caveat I could not eliminate: analyzeAutoTone's 615 untraced indirect/vtable call sites could theoretically still reach it — this is a limit of static direct-call analysis, the same limit the project's own calibration figures carry.

**4. What it writes, and its plausible effect on tone:** `AnsSCPLutResults` — `redSlope`/`greenSlope`/`blueSlope`, `redOffset`/`greenOffset`/`blueOffset`, `slopeDist`, `slopeLimiter`, `visualGamma`. This is a **per-channel affine (gain + bias) transform on R/G/B** — not geometric, cosmetic, or orientation data. It feeds an `Ans3BandLutParams` table (`setShifts(1,2)`, already Unicorn-verified in `pakon_setshifts_golden.py`) that gets pre-composed with `filmLut` and the color/flesh/afterSCPLutSba/sba "shift" LUT into one 3-band table — confirmed today as the same table `balanceAreaImage` and `BalanceMethods_export` build. `pakon_ansel.py`'s own docstring records the output landing at `scene+0x4b6/+0x4b8/+0x4ba`, which `analyzeScpLutBalance` itself first zeroes as "FUGC aim words" (`0x100fd8be`) before the second (`afterSCPLut`) pass overwrites them — i.e. scpLut's own analyze directly manipulates the scene's FUGC aim/tone slots. This is squarely per-pixel-RGB/density-relevant math, applied upstream of FUGC and (per the scene order) upstream of autoTone's own image statistics, even though autoTone doesn't call it by name.

**5. Existing ported/verified code — substantial, not from scratch.** `tools/ansel/python-pipeline/pakon_scp_lut.py` already has: Cap/Impl/acquire/initialize addresses (all re-verified above), full DPI ASCII parsing (`SCP_LUT_DPI_PARSE_PORTED=True`), 3-band LUT ASCII loading (`THREE_BAND_LUT_ASCII_PORTED=True`), and the analyze leaves — opponent transform, slope-distance, LUT index+clamp fill (`SCP_LUT_ANALYZE_LEAVES_PORTED=True`), each cited to the exact addresses I re-verified. Only the actual slope/offset balance-application maths end-to-end is open (`SCP_LUT_BALANCE_PORTED=False`). This is closer to fugc's state (12/13 flags true) than a blank gap — grep confirms no other `tools/` file duplicates or shadows this coverage.
